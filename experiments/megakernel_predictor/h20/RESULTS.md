# H20 常驻 Qwen3.5-35B-A3B 的投影重叠与 B2 切分选择

## 测量设计

使用单张 78 SM、97,871 MiB 的 NVIDIA H20，GGUF 为
`Qwen3.5-35B-A3B-UD-Q2_K_XL.gguf`。专家全部驻留 GPU。每个实验分别固定
gate/up 与 down 的 CUDA CTA 配额为 26/52、39/39 或 52/26。
线程数为 512，gate/up 的输出行分块为 32，down 为 64。

独立的训练捕获提供 8 个 forward，每个 40 层。对每个层和配额用同一个 CUDA
kernel 比较串行与实际重叠，仅切换 gate/up 和 down 之间的全局屏障。每对交替
起始顺序，重复四次，调用前触及 96 MiB 的缓存驱逐缓冲。总共获得 3,840 个
配对的层执行，两种安排的 FP32 输出逐值一致。记录 tile 实际计算的起止时间，
不把 down 等待 expert-ready 的时间计入 tile 计算。服务器的 Nsight GPU 硬件
计数器返回 `ERR_NVGPUCTRPERM`，故报告 tile 服务时间与权重逻辑字节速率。

## 服务时间和重叠

下表的 tile 变化以实际有至少 75% 执行时间与对侧投影重叠的 tile 为样本，
以对应串行 tile 为分母。重叠比例以两个投影的总时间跨度为分母，统计同时有
gate/up 和 down tile 在执行的时段。所有数字均为各自样本的中位数。

| gate/up / down CTA | 实际重叠比例 | gate/up tile 时间增加 | down tile 时间增加 |
| --- | ---: | ---: | ---: |
| 26/52 | 72.37% | 1.06% | 0.46% |
| 39/39 | 47.84% | 0.58% | 0.68% |
| 52/26 | 22.98% | 0.56% | 1.32% |

26/52 的 gate/up 阶段逻辑速率从 140.59 变为 140.20 GB/s，down 从
114.46 变为 89.56 GB/s。速率的时间分母包括 stage 内的就绪间隙。
down 的单 tile 计算只增加 0.46%，因此不能用阶段速率下降估计物理 HBM 争用。
没有跨阶段重叠的 tile，配对时间比的中位数为 1.000。

用带 stage 自身占用变化项的拟合估计对侧 CTA 占用的影响。对侧占满保留配额时，
拟合出的边际服务减速是 gate/up 1.02%、down 0.72%。ComposeDES 在每个事件
窗口用实际活动 tile 数计算对侧占用，每到达 tile 完成事件即更新服务速率。
该回放使用跨配额共用的系数，当前窗口模型只使用拟合的跨阶段项。对投影
\(s\)，用 \(n_{\bar s}(t)\) 表示对侧正在计算的 tile 数，\(q_{\bar s}\) 表示对侧
CTA 配额。设 \(r_i\) 为 tile \(i\) 剩余的串行等效服务时间，窗口内按

\[
\frac{\mathrm d r_i}{\mathrm d t} =
-\left(1+\beta_s\frac{n_{\bar s}(t)}{q_{\bar s}}\right)^{-1}
\]

推进。窗口边界由 tile 完成或依赖释放决定。逐 tile 阶段复算用新的持续时间回填
同一 DAG，抽样复算的 ComposeDES 关键路径与争用窗口回放相差不超过 4 ns。

## 独立留出验证

第一批 16 个新请求检验从投影级服务均摊到 tile 的模型。只加争用系数和继续加
CTA 与 expert-ready 间隙都选择了 39/39，三轮实测均为 26/52 快。误选损失
为 1.73%。随后用原训练捕获直接估计每类 tile 的中位服务时间，分组条件为
投影、量化格式、CTA 配额和该专家实际接收的 token 数。保留同一个事件图和
争用系数，再用另一批 16 个请求验证。第二批先做独立路由捕获，冻结预测文件
并校验 SHA-256，随后计时。每候选三轮，每轮 8 对请求、每对 24 步，去掉前
4 步后留下 160 个 B2 forward。结果取各轮中位数的中位数。

| GGUF 候选 | 逐 tile 预测 ms | 实测 ms | 实测名次 |
| --- | ---: | ---: | ---: |
| 原版 llama.cpp | 6.809 | 6.777 | 1 |
| 整层融合，两阶段复用 78 CTA | 7.648 | 7.658 | 2 |
| 投影间切分，两阶段均用 78 CTA | 7.751 | 7.786 | 3 |
| 就绪流水 26/52 | 8.693 | 8.227 | 4 |
| 就绪流水 39/39 | 8.798 | 8.383 | 5 |
| 就绪流水 52/26 | 10.075 | 9.614 | 6 |

原版由改动前的源码快照 `51e5c9afbbccb353cefd698036ab9ed00a3612ab` 独立编译，保留 CUDA Graph。原版候选的预测值是训练请求
的实测中位数。其余 GGUF 候选用整层融合的训练执行补齐路由专家之外的耗时。
逐 tile 模型对六个 GGUF 候选的 15 个排序对判断正确，26/52 在三轮都最快，
同时三个流水候选的绝对时延仍被高估 0.42–0.47 ms。只增加争用项的模型仍选择
39/39，实测代价 1.90%。五个研究候选各轮均与参考融合算子匹配 384/384 个
argmax，记录的最大 logits 相对 L2 为 0。GGUF 的 GPU 峰值约 12.39 GiB。

配额比较基于已观测路由离线模拟，在线采集、选择及部署开销未测。留出集只验证
了当前 B2 形状，三种配额的实测排序在两批请求中相同。因此结果验证了对固定
配额的选择，没有观察到最优配额随请求改变。

## FP8 MonoMoE 对照

使用 Qwen 官方 FP8 checkpoint 的完整 40 层文本模型。路由专家采用原始
E4M3 权重与 128×128 块缩放，已量化的非路由线性层在装载时转为 BF16，
全部权重和状态在 H20 上。FlashInfer 0.7.4 的单形状 MonoMoE 适配为 64 CTA，
比较 expert-ready 标记、跨 CTA 全局屏障、保留路由元数据的投影间双 kernel。
训练和留出重复使用对应的 GGUF teacher 输入 token。相同 token 允许比较完整
decode 延迟，FP8 与 GGUF 的路由、注意力实现和权重格式各自独立。

首先用独立训练输入的真实激活、路由和官方 FP8 权重，每个切分采集 40 层各
4 次服务计时。对各候选把 40 个 layer median 事件串联，ComposeDES 的关键路径
依次为 1.157、1.222 和 1.272 ms。以 flags 的独立完整模型训练计时补齐注意力、
非路由线性、输出头和框架成本，形成预测并冻结。FP8 各版本的输入 shape、权重
与计时区间一致。GGUF 时延取 `llama_decode` 加等待完成，FP8 取模型前向加等待
完成，均排除预填充和 argmax。

Eager 诊断的预测依次为 70.985、71.050、71.099 ms，留出实测分别为 42.444、
42.795、42.792 ms。耗时对训练提示长度敏感，固定训练中位数高估了留出集。
在整个候选池里其预测排对 35/36 对，只颠倒了两个相差 0.004 ms 且轮间
范围相交的 FP8 对照。这个差值不足以支持两者的细粒度排序。

### 复现材料

- `build_trace.py` 与 `trace.inc` 生成训练投影的配对 CUDA 记录器。
  它连接此前 H20 实验的 `stage_profile.cu`、`resident-moe.cu` 和分块代码，
  使用 `-arch=sm_90 -DQWEN_RESIDENT_STANDALONE -DGGML_CUDA_PEER_MAX_BATCH_SIZE=128`
  编译，并链接 `ggml-base`。用真实训练工作流运行
  `tile_trace_v2 GGUF dev/train-b2.bin 8`。
- `../contention.py TRACE OUTPUT --services SERVICES` 生成校准参数。
  [校准 JSON](contention-h20-b2.json) 含计数、回归项、重叠比例和各 tile 中位数。
- `fp8_full.py`、`fp8_components.py` 和 `run_fp8.sh` 对接先前实验中的
  FlashInfer JIT 特化目录 `tiled/` 与官方模型。预测由 `fp8_forecast.py`
  生成，完整模型和投影服务分别读取独立训练输入。
- 两轮 GGUF 预测 SHA-256 分别为
  `f8167c6c5b307a3b9dd069629180916968c647f6a344ffe5c024325372fd9ee4`、
  `64aa14bbe4ba0d3f33d4a447c8d809601f235a2d9f51605e9b66e5fa5fa90001`。
  逐轮测量 CSV、训练参数和冻结预测已收录在 [复算数据](../replay-data/)。

### CUDA Graph 验证边界

全模型静态 KV 与 recurrent cache 的 CUDA Graph 原型完成了训练试跑，随后在
留出集的首步 logits 校验中失败。恢复原始模型缓存及 MonoMoE scratch 后，
仍观测到相对 L2 约 2.46% 的一例，超过试验设定的 0.2% 阈值，该步 top-1 未变。
相应 Graph 计时保留为诊断，未纳入正式排行。正式 FP8 排名只适用于 eager
后端，不能判断同样使用 CUDA Graph 的 FP8 是否快于原版 llama.cpp。

FP8 的三种 eager 实现彼此每轮 381–383/384 个 top-1 一致，同一实现重跑也
最多相差 4/384 个。全量包均做有限值检查，仍不能声称三个 FP8 实现逐元素等价。
FP8 的峰值为 PyTorch 分配统计的约 34.76 GiB，GGUF 的峰值为 CUDA 设备用量。
