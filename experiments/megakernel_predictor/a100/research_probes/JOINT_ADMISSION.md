# 构图顺序与搬运配置的联合选择

## 固定构图还能留下多少损失

在 A100 PCIe 40 GB 上，把上轮的单一双链扩展成三类依赖。每个配置均运行六组 2,048-token BF16 K/V 读回与七个计算任务，读回总量为 48 MiB。用 SGLang HiCache、CUDA DMA、FlashInfer FA2 与 cuBLAS GEMM 的实际实现。依赖结构借鉴前缀预取、计算释放读回与分支汇合，前两轮均为受控子图。计算释放已知的读回计划，实际的索引与服务调度没有包含在内。

| 功能依赖 | 实验里的结构 |
| --- | --- |
| 搬运链 | 搬运串行预取，计算链消费对应块 |
| 计算触发 | 一个较重的生产者先运行，释放后续读回。另一支可以直接预取 |
| 分支汇合 | 三个长短不一的分支共享 GPU 和读回资源，最终任务等待各分支 |

每类依赖用 attention/GEMM 各三个形状与两种 CPU KV 布局。连续布局的 DMA 按 K 和 V 各一次复制，分散布局对每段连续页面分别提交 DMA。两种方式均读取与 HiCache 一致的已选 KV。每种工作负载测试六个合法的 CUDA Graph 节点创建策略与 DMA、2、8、24、64 CTA。图只保留功能节点，在外部首尾计时。候选正确性检查先用 NaN 覆盖 GPU KV，检查完整 KV 与计算输出。每候选每进程 16 次配对轮次。实际执行了两轮共 33,600 次不同候选的测量。相同节点序列的构图策略共享一次测量。

### 相同算子形状的见证例

固定 1,536-query attention、连续 KV 布局与读回量。表内为进程 B 的配置中位数。不同依赖需要不同计算段长度和功能顺序，行内的所有配置共享相同算子参数、依赖和数据地址。

| 依赖 | 先创建搬运节点＋8 CTA | 更快的实测配置 |
| --- | ---: | --- |
| 搬运链 | 4.487 ms | 先创建搬运节点＋8 CTA，4.487 ms |
| 计算触发 | 5.947 ms | DMA＋随机生成的合法顺序 19，5.275 ms |
| 分支汇合 | 5.762 ms | DMA＋按关键路径创建，4.789 ms |

计算触发结构里，两次进程均选中相同的组合。固定 DMA，仅把先创建搬运节点改成顺序 19，同轮配对收益为 0.697 ms，95% 分层 bootstrap 区间为 0.672–0.714 ms。分支汇合里，进程 A 的最好配置是 DMA＋计算优先，进程 B 是 DMA＋关键路径。用计算优先当作固定对照，两次进程的配对改善中位数均约 0.7 ms。搬运链里 DMA 搬运优先比 8 CTA 搬运优先慢约 18 µs，实际意义较小。

对全部 28 个留出负载，用事后信息选择全局固定组合，也分别测算只放开搬运配置和只放开构图顺序的理想情况。每项差距都相对该负载全部实测配置里的最快值。

| 事后对照 | A 平均差距 | A 最大差距 | B 平均差距 | B 最大差距 |
| --- | ---: | ---: | ---: | ---: |
| 最佳固定组合，2 CTA＋交错创建 | 1.86% | 11.35% | 2.39% | 14.93% |
| 最佳固定顺序，搬运优先，每个负载允许选实测最快的搬运方式 | 1.24% | 11.14% | 1.80% | 11.21% |
| 最佳固定搬运方式，2 CTA，每个负载允许选实测最快的顺序 | 1.69% | 11.35% | 2.23% | 14.93% |

这两个控制把结构变化造成的调度空间与单纯换用 DMA 分开。以上结果限于测过的依赖、候选以及 GPU。

另做了一组配平对照，把三类依赖的七段计算都固定为相同的规模序列 `(3, 2, 1, 1, 1, 1, 1)`，同时保留 1,536-query 基础形状、连续布局与 48 MiB 读回量。两轮均选 DMA，但三类图分别选中关键路径优先、顺序 19 与交错创建。只在这三个配平负载上，事后最佳固定组合为 DMA＋顺序 19，平均差距 0.61%–0.71%，最大差距 1.09%–1.17%。这组对照把依赖的影响从计算量差异中拆出来，也限定了单靠改变依赖所能观察到的收益规模。

## 第一版 ComposeDES 准入模型

由原有 WorkflowController 跟踪功能依赖。建模 worker 把已就绪的任务放入候选队列，以节点创建位置和下游关键路径长度形成优先级，检查 CTA 容量和 DMA 引擎可用性。事件发生时重新计算所有任务的速率。原生 HiCache 搬运会占用 CTA 资源，DMA 使用单独的 copy engine；两类传输都可以与计算竞争内存路径。模型没有增加功能依赖边，也没有设置每节点拟合参数。

训练只用搬运链、两个已见形状、两种布局的八个组合。四个共享参数为创建顺序权重、计算活跃时可留给搬运的 CTA 容量、SM 搬运对计算的速率惩罚和共同内存路径的惩罚。预设 54 组参数，用平均配对排序损失挑选。训练需要 140 个不同端到端配置，每个 16 次回放。每个训练或测试负载均另外测 37 个独立阶段，每阶段 7 次计时。测试标签使用独立进程 B。零目标端到端测量的模型可以使用进程 A 的目标阶段隔离计时。Nsight Systems 仅用于训练完成后的机制核对。

### 留出结果

表中是零目标端到端测量时，相对各测试池内实测最快配置的平均差距。关键路径启发式用事先设定的阶段工作量生成顺序，搬运方式按布局从训练集确定。固定方案亦由训练集确定。

| 方法 | 新形状，4 个 | 新依赖，8 个 | 新依赖＋未见创建顺序，12 个 |
| --- | ---: | ---: | ---: |
| 最佳训练固定组合 | 0.00% | 0.61% | 4.14% |
| 按布局选固定组合 | 0.01% | 0.62% | 4.85% |
| 关键路径优先 | 1.24% | 3.21% | 4.36% |
| ComposeDES 功能 DAG | 0.03% | 0.72% | 6.92% |
| 顺序特征岭回归 | 0.30% | 2.79% | **3.31%** |
| ComposeDES 准入模型 | 0.03% | 2.50% | 4.54% |

新形状与新依赖两列保留四个训练期使用的构图规则，以分别检验形状和依赖变化。分支汇合列包括六个构图规则，其中两个随机拓扑顺序从未用于训练。一部分分支汇合负载的算子形状也未见过。仅在陌生顺序之间选择的结果另见 `selection.json` 中的 `new-order-only`。这一严格子集上的最强方法是关键路径规则的最近合法顺序，平均差距 1.88%，回归为 2.33%，准入模型为 3.18%。

预算从 0、1、2、4、8、16 到全测。一个预算单位是进程 A 中候选的 16 次首尾计时。所有方法共享包含最佳训练固定组合的随机候选前缀。直接搜索选已测最快。预测方法用观测中位残差修正未测候选的分数，再与已测候选竞争。新依赖及新顺序一列上，测 8 个候选时直接搜索、回归和准入模型的平均差距分别为 2.64%、3.32%、3.91%。用进程 A 的全测选择，到独立进程 B 仍有 1.37% 的平均差距。预算曲线同时包含跨进程差异。

## 下一版先把资源准入假设做对

仅在搬运链上标定时，最优参数给创建顺序的权重是 0，内存路径干扰也取 0。该训练集的最优配置几乎固定，从端到端值无法稳定识别竞争任务如何进入执行。另有一个可以直接定位的结构错误。模型规定任一时刻至多运行一个计算任务。独立 Nsight 采样在计算触发的 DMA 路径中测到约 0.133 ms 的两个 attention kernel 并发。在相同的计算触发图里，DMA 优先和实测最佳顺序的累计 DMA 均约 4.15–4.16 ms，计算与 DMA 的真实重叠从 1.55 ms 增加到 2.14 ms。模型需要表达并发计算和共享资源下的实际准入，而非为每个节点补一个延迟。

后续可以用少数有意制造并行就绪的训练图，例如两个短 compute 节点竞争一个长 compute 节点的剩余 CTA 容量、两个 DMA 读回竞争后续消费顺序。加入部署框架中的实际依赖子图做独立留出。优先判断共享参数能否被这些端到端测量识别，并在相同预算下超过回归和直接搜索。当前数据支持继续研究联合选择，当前模型还未验证选型收益。没有扩展候选到融合边界，也没有把稀疏 KV 结果加入训练。

## 复现

沿用同目录的 CUDA 13 图回放库。下面的命令在本目录运行，模型分析需要 NumPy，绘图需要 Matplotlib。

```bash
nvcc -std=c++17 -shared -Xcompiler -fPIC explicit_graph.cu -lcuda -o libexplicit_graph.so
mkdir -p ../../runs/mpk-a100/joint-admission
for session in A B; do
  python joint_probe.py --session "$session" --repeat 16 --output "../../runs/mpk-a100/joint-admission/joint-$session.jsonl"
  python joint_probe.py --session "$session" --matched --repeat 16 \
    --output "../../runs/mpk-a100/joint-admission/matched-$session.jsonl"
done
nsys profile --trace cuda,nvtx --cuda-graph-trace=node --sample=none --cpuctxsw=none \
  -o ../../runs/mpk-a100/joint-admission/joint-node \
  python joint_probe.py --session A --profile --repeat 8 \
  --output ../../runs/mpk-a100/joint-admission/joint-node.jsonl
nsys export --type sqlite -o ../../runs/mpk-a100/joint-admission/joint-node.sqlite \
  ../../runs/mpk-a100/joint-admission/joint-node.nsys-rep
python evaluate_joint.py ../../runs/mpk-a100/joint-admission
python audit_joint.py ../../runs/mpk-a100/joint-admission
python plot_joint.py ../../runs/mpk-a100/joint-admission
```
